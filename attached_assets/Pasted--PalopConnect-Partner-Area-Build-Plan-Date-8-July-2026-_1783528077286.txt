## Phase 0 — Prerequisites

### P0.0 — Fix commission rate trigger ⚠️ URGENT — do before any new partner sales

**Problem:** The live trigger `record_partner_commission_on_order()` calculates rate based on order price. Correct logic is volume-based: 15% for sales 1–49, 20% from sale 50 onwards.

**Required change 1 — Fix the rate logic in the trigger.**

Replace the price-based CASE expression with the following. Use the actual variable names from the existing trigger source — do not copy-paste blindly; verify variable names first:

```sql
-- Count non-cancelled completed commissions for this partner before this insert
SELECT COUNT(*) INTO v_completed_sales
FROM partner_commissions
WHERE partner_code = NEW.referral_code  -- use whatever variable holds the code in the existing trigger
  AND status NOT IN ('cancelled');

v_rate := CASE WHEN v_completed_sales >= 49 THEN 0.20 ELSE 0.15 END;
```

Key points:
- Use the correct variable name for the partner code as it appears in the existing trigger body — do not assume `v_partner_code`
- Exclude `cancelled` rows from the count — a cancelled commission must not inflate the volume tier
- Sale #50 correctly gets 20%: when 49 non-cancelled rows exist, `v_completed_sales = 49 >= 49` → 20%

**Required change 2 — Add `rate` column to `partner_commissions`:**

```sql
ALTER TABLE partner_commissions
ADD COLUMN IF NOT EXISTS rate numeric NOT NULL DEFAULT 0.15;
```

Update the trigger to store the computed `v_rate` into this column on every insert.

Update the existing 1 row: `UPDATE partner_commissions SET rate = 0.15` (confirmed correct — first sale, 15% tier).

**Verification:**
- Show the full updated trigger function body
- Confirm existing row has `rate = 0.15`

### P0.1 — Add `partner` value to `app_role` enum

`profiles.role` is a Postgres enum of type `app_role` (not a CHECK constraint). Adding `partner` requires:

```sql
-- Migration 1: add enum value
ALTER TYPE app_role ADD VALUE 'partner';
```

This must be committed as its own migration before any statement that uses the new value `'partner'`. In Postgres, a newly added enum value cannot be used in the same transaction that adds it.

Do not change any existing profile rows. After migration: confirm all existing profiles retain their current role.

### P3.1 — New table: `consignment_orders` ← MOVED HERE (must precede edge function)

```sql
CREATE TABLE consignment_orders (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  partner_id     uuid NOT NULL REFERENCES auth.users(id) ON DELETE RESTRICT,
  partner_code   text NOT NULL,
  batch_id       text,
  plan_name      text NOT NULL,
  quantity       integer NOT NULL CHECK (quantity > 0),
  unit_price     numeric NOT NULL CHECK (unit_price >= 0),
  total_value    numeric GENERATED ALWAYS AS (quantity * unit_price) STORED,
  status         text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'paid')),
  paid_at        timestamptz,
  notes          text,
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now()
);

ALTER TABLE consignment_orders ENABLE ROW LEVEL SECURITY;
```

**RLS policies:**

```sql
-- Admin: full access
CREATE POLICY "Admins can manage consignment orders"
ON consignment_orders
FOR ALL
USING (get_current_user_role() = 'admin')
WITH CHECK (get_current_user_role() = 'admin');

-- Partner: read own rows only (defence in depth — primary access is via edge function)
CREATE POLICY "Partners can view their own consignment orders"
ON consignment_orders
FOR SELECT
USING (auth.uid() = partner_id);
```

## Phase 1 — Partner data edge function

### P1.1 — New edge function: `get-partner-dashboard`

**Prerequisite:** P3.1 must be deployed before this function is deployed.

**Location:** `supabase/functions/get-partner-dashboard/index.ts`

**CORS headers:** Include `sentry-trace` and `baggage` in `Access-Control-Allow-Headers` — required for preflight to pass (established codebase pattern from June).

**Logic (in order):**

1. Read the caller's authenticated session from the request JWT. If no valid session: return 401.
2. Look up `profiles.role` for `auth.uid()`. If role is not `partner`: return 403.
3. Query `referral_codes` where `user_id = auth.uid()` AND `type = 'partner'` AND `is_active = true`. Extract `code` and `id`. If not found: return 404 with message "No active partner code found."
4. Using the **service role key**: query `partner_commissions` where `partner_code = <their_code>`, ordered by `commission_date DESC`. Return all rows.
5. Using the **service role key**: query `consignment_orders` where `partner_id = auth.uid()`, ordered by `created_at DESC`. Return all rows.
6. Compute summary totals server-side:
   - `commission_total_earned`: sum of `amount` where `status IN ('owed', 'paid')`
   - `commission_total_paid`: sum of `amount` where `status = 'paid'`
   - `commission_total_pending`: sum of `amount` where `status = 'owed'`
   - `consignment_total_pending`: sum of `total_value` where `status = 'pending'`
   - `consignment_total_paid`: sum of `total_value` where `status = 'paid'`
   - `total_sales_count`: count of `partner_commissions` rows where `status NOT IN ('cancelled')` (more truthful than `uses_count`)
7. Return JSON payload:

```json
{
  "partner": {
    "code": "PRAIATUR",
    "label": "Praiatur",
    "total_sales_count": 1
  },
  "summary": {
    "commission_total_earned": 0.00,
    "commission_total_paid": 0.00,
    "commission_total_pending": 0.00,
    "consignment_total_pending": 0.00,
    "consignment_total_paid": 0.00
  },
  "commissions": [...],
  "consignment_orders": [...]
}
```

**Logging rules:** Do not log customer email addresses, full order IDs, or financial amounts. Log only: function invoked, partner_code resolved, row counts returned, errors.
