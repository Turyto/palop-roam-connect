Assessment of the root cause diagnosis
The developer is correct. The current flow has a fundamental design flaw:
Browser → Stripe (payment captured) → Browser → Supabase INSERT (can fail)
Money is taken before the order record exists. The browser's Supabase write is protected by RLS (auth.uid() = user_id), but for anonymous/guest sessions — which is how most customers check out — the anon session identity at payment-initiation time and at insert time can diverge, especially under any network latency or tab behaviour between those two steps. The June 16 success was the exception; the current failure is the rule.
One thing the report doesn't explain but matters: something changed between 16 June (1 success) and 18 June (consistent failures). The most likely candidates are the World Cup section deployment or a recent Replit/Supabase session handling change. Worth a 10-minute investigation to understand — but crucially, the architectural fix makes the cause irrelevant going forward.

Assessment of the proposed fix
The recommended direction is correct. Server-side order creation at create-payment-intent time is the standard pattern for exactly this class of problem. The correct flow becomes:
Browser → Edge Function: create-payment-intent
         ↳ Server writes pending order row (service-role, bypasses RLS)
         ↳ Returns clientSecret + order_id to browser
Browser → Stripe (payment captured)
Stripe → Webhook → Edge Function: marks order paid → provisions eSIM → sends email
The order exists before money is taken. A browser crash, network drop, or session glitch cannot produce a "charged but no record" outcome. This is architecturally sound.

Implementation notes for the developer (where I'd push back / add detail)
1. The webhook must be idempotent. The Stripe webhook will fire payment_intent.succeeded. The handler must check whether the order is already in completed state before provisioning — Stripe can retry webhooks, and duplicate eSIM provisioning is a real cost. Use ON CONFLICT DO NOTHING or a status check guard.
2. Stripe webhook signature verification must be enforced. If it isn't already verifying Stripe-Signature header against STRIPE_WEBHOOK_SECRET, add that immediately. An unverified webhook endpoint is a security hole that could allow anyone to fake a "payment succeeded" event and receive a free eSIM.
3. Handle the payment_intent.payment_failed event too. When payment fails after the pending order is created, the webhook should mark the order failed — otherwise the admin dashboard will accumulate stale pending rows for every failed card attempt.
4. The customer_email problem. Currently customer_email is written by the browser at order creation time. If the order is created server-side at payment-intent time, the email must be passed as a parameter to the edge function (not read from the session), because for guest checkouts the customer enters their email in the Stripe form — which is after the order is created. Consider: store customer_email as nullable in the pending order, then populate it from the Stripe checkout metadata or payment_intent.metadata when the webhook fires.
5. Pending order cleanup. Add a scheduled Supabase function (or manual cron) to cancel orders that remain pending for >30 minutes with no Stripe confirmation. Otherwise your admin dashboard will fill with ghost rows from abandoned checkouts.
